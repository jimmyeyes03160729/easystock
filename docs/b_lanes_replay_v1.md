# B1／B2／B3 完整輸入回放 v1

回放直接呼叫 `LaneSuite`，不另寫一套近似進出場規則、不重用舊 B 帳本、不呼叫券商或訊息服務。三條每日累計進場各100萬元等規則與即時跑道相同（不限股價）。

## 輸入與品質

`InputRecorder` 在策略鎖內依接受順序記錄 seed、逐筆、五檔、radar、release、clock，背景執行緒壓縮寫檔。radar 保存實際股票池、昨收、產業、先賣後買資格、已完成五分K與大盤判斷；clock 保存當時判斷時間與決策後狀態雜湊。seed 保存啟動／重啟的已知帳本狀態。來源有 queue 掉筆、寫檔錯誤、未正常關閉或雜湊不符時，不列正式績效。

預設位置 `/home/ubuntu/easystock-runway-v2/recordings/YYYY-MM-DD`。可用 `RUNWAY_B_REPLAY_DIR` 指定根目錄，`RUNWAY_B_REPLAY_RECORDING=0`停用。每次程序最多錄製1GiB，磁碟剩餘不足2GiB停止寫入並標記不完整，不自動刪除既有資料。長期錄製仍需監控空間、安排封存；此版沒有NAS同步。錄製及回放不會改動原始歷史資料。

回放採當時接受順序，不依事後得知的交易所時間重新排列。可用資料只取該clock以前的已接受輸入。延遲情境保留原始行情時間，不把舊報價偽裝成新鮮報價。資料按串流讀取，不將整天逐筆展開放入記憶體。

完整日須涵蓋09:00至該跑道結束，判斷clock間隔不能超過30秒、該時段有逐筆與五檔、有股票池與有效大盤資料；B1有產業分類，B2至少20根、B3至少3根完整五分K。來源指紋必須與現行規則一致。前日未平倉、回放state hash不符、最後狀態不符都不計正式績效。已開始回放但仍待取得報價平倉的日期另列pending。

這代表「當時訂閱池及策略輸入已完整保存」，不是全市場行情完整，也不保證券商來源沒有漏包。市場或個股來源中斷可能只反映為報價過期拒絕；保留此限制，不宣稱逐筆資料絕對無遺漏。歷史逐筆的買一／賣一不等同五檔；五分鐘取樣研究journal亦不等同逐筆或完整即時股票池。

## 指標與成交假設

- 每條分列有效／排除／待平倉天數、已平倉筆數、淨損益>0的勝率、費後淨損益、平均每筆淨損益、最大已實現回撤。
- 費用沿用買賣各0.1425%×28折、賣出當沖稅0.15%及取整方式。做多賣一買入／買一賣出，做空反向；第一檔深度不足不宣稱整筆成交。
- 基準回放為可見報價模擬，不含排隊、自身市場衝擊與實際券商回報。
- 500ms／1000ms：延後逐筆與五檔對策略可用時間，重跑同規則；不是更改交易所時間，也不是保證可在該毫秒成交。股票池與clock不延後。
- 雙邊各多一檔：固定基準交易集合，淨損益額外扣 `股數×(進場價檔位+出場價檔位)`，不重新計算進場、停損路徑、稅費或限額，因此只是成本敏感度。
- 延遲下仍未平倉的日子不計該情境績效；各情境有效天數可能不同，不能直接以未平倉排除後較高數字宣稱更好。
- 回撤只計按出場時間排列的已實現淨損益，未含持倉浮虧。
- `stale_exit_checks/exit_quote_checks`、`thin_exit_checks/exit_fill_checks`、`thin_entry_checks/entry_fill_checks` 是按clock重試機會計算的比例，並非獨立委託或獨立股票比例。不同拒絕類型分母不同。

## 每日比對與排程

基準每個clock均比對錄製時state hash，結束比對manifest final_state；若當日live SQLite存在，另比對其持倉、交易、累計金額和進場數。錄製hash一致只能證明回放一致，不能證明模擬等同實際成交。

每日13:20／21:20執行資料盤點與回放，結果存 `replay-latest.json` 並發布 `/market_data/public_feed/b_lanes_replay`，首頁顯示三條績效、壓力情境、資料品質與日別排除理由。盤點預設近183個日曆日，CLI可指定 `--since`／`--until`。未有有效日的績效欄位為null，不能以0元或0%冒充回測結果。

離線：`python -m runway_v2.replay --record-root <recordings> --history-root <archive> --output <report.json>`。只有明確帶 `--publish` 才寫Firebase；任何模式均不發LINE、Telegram。

目前已有歷史逐筆與分鐘K，但未找到完整五檔及新版完整輸入檔，因此仍無可核實的新B跑道歷史勝率。測試的合成資料只驗證回放機制，不列入正式結果。

已檢查且原始檔雜湊與持久帳本均未變動的日期會使用快取，避免每天反覆重跑全部逐筆；原檔、規則或帳本改動即失效。成交資料檢查比例包含已完成與仍待平倉的可核對日期，避免只看順利平倉的日子。

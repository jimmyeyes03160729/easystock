## 二、四種「AI／學習」要分開驗收

| 流程 | 實際用途 | 是否會更新翌日進場模型 |

| 盤前 Gemini | 文字摘要、新聞建議；新版硬風控採 base_risk_score | 不會 |
| 盤中數值模型 | 讀固定 artifact，計算邏輯迴歸分數；須 model 模式、核准、特徵完整及達門檻 | 本身不訓練、不自動換檔 |

目前日內研究的 5 欄是 gain_pct、return_5m_pct、surge_60s、buy_ratio_60s、amount_60s。

## 三、目前完整當沖流程

以下是程式預設值；VM 環境或後台可以覆蓋部分參數。timer 時間已由 VM 輸出確認。

### 08:35 盤前

1. systemd 執行 root premarket_ai.py，轉入 vm_runtime/premarket_ai.py。
2. 檢查市場日曆；休市或檢查例外返回。FORCE_PREMARKET_AI 若設 1 會略過已知休市判斷，使用者貼出的環境檔未見此設定。
3. 建立盤前資料，寫入 Firebase premarket_brief。日期與 base_risk_score 必須有效；缺失時新版當沖將阻止新進場。

### 08:55 啟動／09:00 暖機

1. 當沖 timer 觸發 root intraday_live.py。開盤日檢查失敗不啟動引擎。
2. 初始化模擬帳本、恢復同日部位／已做過股票。跨日未對帳部位會阻止直接清除舊資料；啟動失敗需修復帳務問題。
3. 登入 Shioaji、裝設 callback，訂閱需追蹤部位；09:00 開始市場活動股掃描。
4. Scanner 活動池預設 170 檔、60 秒更新；雷達最多 30 檔、3 秒更新；使用 10/30/60 秒成交與數分鐘基準。
5. 每 15 秒 heartbeat，主迴圈約 0.5 秒。heartbeat 新鮮不保證報價新鮮，需另檢查 quote/radar。

### 09:30–12:30 新进場

1. 須在進場時段、有足夠 5/15 分 K 暖機、進入當前候選股。
2. 雷達預設：60 秒量能倍數至少 1.8、買盤比例至少 55%、可分類成交至少 50%、60 秒量至少 20、金額至少 300 萬、60 秒價格動能至少 0.05%。實際值須由 VM 核對。
3. 每 30 秒更新盤前／指數風險。指數快照超過 90 秒、日期不對或讀不到時阻止新進場。風險有效期最多 45 秒；指數跌幅 -1% 黃、-2% 紅；盤前 base score 與即時等級取較嚴格者。
4. `rules` 模式：score>=76、至少兩理由、無 veto。分數權重：型態30%、量能20%、VWAP15%、市場10%、流動性10%、historical_edge15%。historical_edge 是既有策略輸入，不等於當天重訓 AI。
5. veto：低於 VWAP 約0.2%、高於 VWAP 超過3%、上影風險、5分K破短低、市場紅燈。
6. `model` 模式：保留 veto、候選池及風控；改由核准模型特徵與分數判斷，不要求規則分數76。沒有有效模型就不進場，不隱性退回 rules。
7. 再查新鮮報價、價格區間、漲幅限制、每日上限、是否重複做過。
8. SQLite 模擬買進成功才發 ENTRY。帳戶需 running、有足夠可用資金；計入其他持倉保留額與手續費，單檔最多約帳戶資金80%，按整張計算。
9. 記錄研究 ENTRY，發布 Firebase、模擬遊戲及依設定通知。通知成功、策略訊號或網頁卡片都不能代替 SQLite 成交證據。

### 持倉、12:30 截止、12:55 平倉、13:00 結束

| 條件 | 程式預設 |
|---|---|
| 固定停損 | -0.8% |
| 動態保本 | 曾達+0.6%，回落至進價+0.35%時出場；跳空／成本仍可能影響結果 |
| 固定停利 | +1.2%，fixed/hybrid 啟用 |
| 移動停利 | +0.6%啟動，最高價回落0.4%，trailing/hybrid 啟用 |
| 技術出場 | 開啟時，跌破VWAP或5分K破短低可直接出場 |
| 12:30 | 停止新進場，保留持倉追蹤 |
| 12:55 | 模擬強制出場；結算失敗保留部位、每5秒重試 |
| 13:00 | 結束當日引擎；未解決部位需明確列為異常 |

預設仍是 hybrid，因此+1.2%固定停利仍可能先觸發。並未以收益研究證明改 trailing 較好。
強平在報價不足時可能採最後已知價格，不能當成真實可成交價。
模擬帳務用雙邊手續費、賣出稅；研究標籤另有較保守成本／滑價假設，兩者收益不能直接比較。

### 盤後及隔天

- 使用者之前貼出的 VM 排程含13:35摘要、13:40 learning、13:55 paper-feedback、04:30 paper-train；各服務實際參數和成功紀錄尚待本次稽核。
- 新 research-cycle 預定16:10，先收集／標籤再訓練；先前 VM 查到未安裝。不能直接再裝一套而不先核對舊排程是否重複。
- 日內樣本不只記成功 ENTRY；會對活動池按5分鐘區間收集，讓未入選股票也有研究資料。缺失／過期資料不得補零冒充完整。
- 當日沒樣本則跳過。不同成本／出場設定 profile 不混訓。
- 新候選訓練要求同 profile 至少101個日期、1000個樣本，類別也須足夠；不滿足會 blocked，不是訓練成功。
- 有候選檔仍不是隔天自動採用。必須有前向驗證、模型核准、明確路徑與 model 模式，且啟動／ENTRY 證據能對上檔案 SHA。

## 四、績效不佳目前能說到哪裡

尚無本次取得的完整日別／逐筆模擬資料，不能把虧損歸因於某個模型或聲稱某次改動會改善勝率。
已確認可能干擾評估的實作問題包括：舊版訊號與實際模擬成交不同步、資料來源版本不一致、顯示日期誤導、日內上限與文件不符、研究標籤與實際 exit／成本不同。

正確評估要按每筆 entry_time／trade_id 對應 decision_mode、model SHA、當時參數；再區分規則單、AI單、未成交訊號。
至少要統計交易數、扣成本總損益、平均單筆、勝率、最大回撤、出場理由、報價延遲、資料缺漏與策略版本。
模型版本名不等於模型效果，也不能把7個學習日當成7次有效模型上線。

## 五、防中斷仍未驗收的地方

1. **9/16 根因未知**：截圖的09/16 13:49:47欄位是「隔日衝最後掃描」，不能直接當成 Shioaji 當沖引擎的死亡時間；需要 intraday service 日誌與當日樣本。
2. **守護程式 schema 風險**：repo ops/guardian/live.py 查 entry_date、paper_trade_fills；目前新帳本使用 entry_time，且新公開快照不含 shares，舊守護對帳可能報錯。需要核對 /opt 已安裝版本與實際資料庫，不直接擴大自動修復權限。
3. **守護 baseline**：目前引擎 SHA 已更新；舊 baseline 若未審閱更新，會阻止無人值守重啟。guardian-proxy active 不等於 guardian 檢查及修復成功。
4. **systemd 重啟規則未取證**：timer enabled 只證明每天觸發，不能證明盤中崩潰自動拉起。須查 Restart、Result、NRestarts 及 journal。
5. **外部資料可阻擋啟動或進場**：券商登入、訂閱／指數權限、Firebase、跨日未對帳部位、盤前資料缺漏；需要明確異常狀態，不能把沒有交易一律寫成正常等待。
